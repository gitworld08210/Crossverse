## High-level view

The v2 #1 far-path gap is the one that mattered for the user intent, and it is closed properly. `RelayClient.connect()` now establishes the subscribed sockets and then parks on `awaitCancellation()`, so the connect scope stays alive even with zero initial pairings (the fresh-install case). `addPairing()` records the pairing in a shared `PairingSubscriptions` set and, if the pairing is new and `connect()` is already running, launches a fresh `connectPairing` loop into that same scope. The dedup and liveness guarantees are carried by `PairingSubscriptions`, which is pure JVM and now unit-tested.

The wiring is complete end to end. `PairingManager.createPairing`, `acceptPairing`, and `recordPeer` each fire `onPairingSubscribed(pairingId)`, which both transport owners (`SyncService.onCreate` and `LinkupContainer.router`) set to `TransportRouter::subscribePairing`, which calls `relay.addPairing`. A pairing done at runtime therefore reaches a live relay connect loop through a traced, single path, and the first PAIRING_HELLO for that pairing can traverse the relay without a restart.

`addPairing` is idempotent and thread-safe: the new/duplicate decision is made inside `PairingSubscriptions` under a lock, so re-adding a pairing (createPairing then a later recordPeer for the same id) never spawns a duplicate loop, and the callback is safe to invoke from arbitrary pairing-completion threads. The zero-pairings `connect()` does not busy-loop — it suspends on `awaitCancellation()` rather than spinning — and each per-pairing loop keeps its capped backoff, so there is no new leak or hot loop.

The short-code cleanup (v2 #2) is done in code and docs: `Pairing.generateShortCode()` / `PairingManager.generateShortCode()` and the short-code constants are gone, `:core` ships no generator, and the ARCHITECTURE pairing flow no longer lists the "(b) 8-char short code" branch. The one leftover is a dangling `[shortCodeFor]` KDoc reference in `createPairing`.

Test coverage for the new logic (v2 #3) now exists where v2 said it was missing: `PairingSubscriptionsTest` exercises the grow-at-runtime behavior that the startup-snapshot bug violated. The Android-side wiring (`addPairing` launching a real socket, the `onPairingSubscribed` callback chain) still can't be assembled here without the Android SDK and is judged by inspection; that is a known environment constraint, not a gap introduced by this fix.

### Far-path subscription grows at runtime — v2 #1 closed

The fix separates the two things the old snapshot design conflated: the set of pairings a device holds a relay socket for, and the lifetime of the connect scope. `PairingSubscriptions` (new, in `:core`) owns the set — a lock-guarded `LinkedHashSet` whose `add` returns true only on first insertion of a non-blank id. `RelayClient` owns the coroutine side effects and delegates all set decisions to it.

`connect()` snapshots the subscriptions, launches one `connectPairing` loop per id, and then launches `awaitCancellation()`:

```
suspend fun connect() = coroutineScope {
    connectScope = this
    for (pairingId in subscriptions.snapshot()) launch { connectPairing(pairingId) }
    launch { awaitCancellation() }   // keep scope alive with zero initial pairings
}
```

That `awaitCancellation()` launch is what makes the fresh-install case work: with no paired devices, the loop set is empty, but the scope stays alive instead of returning, so a later `addPairing` has a live scope to launch into. `addPairing` records the id and, only if it is new and `connectScope` is set, launches the loop:

```
fun addPairing(pairingId): Boolean {
    val isNew = subscriptions.add(pairingId)   // false if blank or already present
    if (!isNew) return false
    val scope = connectScope ?: return false   // not connected yet: already recorded, picked up by connect()
    scope.launch { connectPairing(pairingId) }
    return true
}
```

The ordering edge case is handled correctly: if `addPairing` runs before `connect()` (e.g. `onPairingSubscribed` is set in `SyncService.onCreate` before `router.start()`), `connectScope` is null and `addPairing` returns false, but the id is already in `subscriptions`, so when `connect()` runs moments later its `snapshot()` includes it and launches the loop. No pairing falls through the crack between "recorded" and "connected."

`connectPairing` is unchanged: it sends the `Hello(deviceId, pairingId)` frame first (matching the relay's handshake), then reads frames into `incoming` and retries under capped backoff on failure. The first pairing's PAIRING_HELLO and subsequent clipboard/file/screenshot envelopes therefore ride a socket handshaked for that exact `(deviceId, pairingId)` — the far path is live for a pairing made while the app runs, which is the user's "phone is far away" case right after onboarding.

### Wiring is traced end to end

Every pairing-completion path fires the callback: `createPairing` (initiator, right after persisting the fresh secret), `acceptPairing` (scanner / paste, the fresh-install first-pairing entry), and `recordPeer` (initiator learning the peer from a runtime PAIRING_HELLO). Each calls `onPairingSubscribed?.invoke(pairingId)`. Both transport owners set that callback to `TransportRouter::subscribePairing`, which calls `relay.addPairing`. `SyncService.onCreate` wires it on its own `PairingManager`; `LinkupContainer.router` wires it on the singleton `PairingManager` the Compose UI drives. Whichever instance the active pairing flow uses, the subscription fires on that same instance's router, so the chain is internally consistent despite the pre-existing two-instance split (that split is unchanged from the base and out of scope here).

### Idempotency, thread-safety, no busy-loop or leak

The new/duplicate decision lives entirely inside `PairingSubscriptions.add` under its lock, so concurrent `onPairingSubscribed` invocations from different pairing threads can't both see a pairing as new and double-launch. `createPairing` followed by a later `recordPeer` for the same pairing results in exactly one loop. Blank ids are rejected at the set, so the `ifEmpty { listOf(deviceId) }` placeholder and any empty id never spawn a stray loop beyond the intended placeholder socket. The zero-pairings scope parks on `awaitCancellation()` (one suspended coroutine, not a spin), and each loop retains its own capped backoff, so the change adds no hot loop and no new unbounded resource.

### Short-code removal — v2 #2 closed, one doc remnant

`Pairing.generateShortCode()`, `PairingManager.generateShortCode()`, and the short-code length/charset constants are gone; `:core`'s `Pairing` object ships only the secret/payload helpers, and its KDoc states no short-code generator exists. The ARCHITECTURE pairing-flow no longer lists the "(b) 8-char short code" branch — the grep for `8-char` / `(b)` finds only prose explaining why there is no short code. README and ROADMAP match. The DevicesScreen `shortCode` state variable is a misnamed binding for the "Paste pairing payload" field, which feeds `acceptPairing` (full-payload JSON parse) — functionally correct, cosmetic naming only. The lone genuine remnant is the `[shortCodeFor]` reference in `createPairing`'s KDoc (Issues #1).

### Test coverage for the grow-at-runtime logic — v2 #3 closed

`PairingSubscriptionsTest` (7 JVM tests) targets exactly the behavior the startup-snapshot bug violated: `fresh install starts empty`, `first pairing after startup is reported as new` (the add-returns-true that triggers a loop), `adding is idempotent and never duplicates a loop`, `second distinct pairing added later is new` (phone↔tablet then phone↔laptop while running), construction dedup/blank-filter, blank-never-subscribed, and insertion-order snapshot. These would fail against a frozen snapshot set, so they lock the fix in. `PairingTest` dropped its short-code assertions. The Android glue (the actual socket launch, the `onPairingSubscribed` chain) remains inspection-only because `:app` can't be assembled without the Android SDK — the known environment constraint, not a new gap.

### Relay untouched and still zero-knowledge

The fix commit does not modify `relay/src/main`. Re-reading confirms no `open`/decrypt/`deriveLinkKey` call there; the only matches are comments asserting the relay never decrypts. Routing stays on cleartext ids. The off-LAN property the "phone is far away" requirement depends on is intact, and the new client-side subscription changes nothing about what the relay sees.
