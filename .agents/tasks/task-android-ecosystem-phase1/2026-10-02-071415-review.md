# Linkup Phase 1: multi-module Android ecosystem with LAN + zero-knowledge relay sync (v1)

Phase 1 scaffolds Linkup — Universal Clipboard, screenshot share, and file/photo share across the user's all-Android devices — as a Gradle multi-module project: a pure-JVM `:core` (wire protocol, AES-256-GCM E2E crypto, HKDF link-key derivation, pairing), a Ktor WebSocket `:relay`, and the Android `:app`. The design cleanly separates the two transports behind one sealed `Envelope`: a NEAR path (NSD discovery + direct TCP socket) and a FAR path (relay WebSocket), which is what makes "works even when my phone is far away" real — a remote phone on mobile data reaches its tablet through the relay, and messages sent while a device is asleep are parked in a bounded offline queue and flushed on reconnect. The crypto and relay routing are genuinely end-to-end: the relay only ever moves opaque ciphertext, verified by both reading `relay/src/main` (no `open`/decrypt call anywhere) and the relay tests, which build and decrypt envelopes with the real `:core` codec.

Watch for: the screenshot feature will crash at runtime on API 29+ because `SyncService` is a `dataSync` foreground service with no `mediaProjection` type or permission (confirmed); the initiator side of a pairing never records its peer, so after showing a QR the initiator can send nothing (confirmed); concurrent file transfers within one pairing corrupt each other because inbound chunks are attributed to "the first in-flight transfer" (confirmed); and the advertised short-code pairing path is cosmetic — nothing resolves a typed code to a payload (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The protocol/crypto foundation is solid and well-tested. Link keys are derived with HKDF-SHA256 from a 32-byte pairing secret, payloads are sealed with AES-256-GCM under a per-link key, and the same serialized `Envelope` crosses both transports. There is no hardcoded key material; secrets live only in `EncryptedSharedPreferences` and link keys are derived on demand, never stored.

The relay is a true zero-knowledge router. It keys live sessions by `pairingId -> deviceId`, forwards sealed envelopes to the other devices in a pairing, rejects frames that spoof a `fromDeviceId`/`pairingId` other than the one handshaked, and parks envelopes for offline peers in a TTL-bounded per-device queue. It never holds a key or calls any decrypt path.

The remote-operation requirement is met at the transport level: `RelayClient` keeps an auto-reconnecting WebSocket open from inside the foreground service, and `TransportRouter` prefers LAN when a peer is present and falls back to the relay otherwise. The relay offline queue covers the "phone was briefly asleep" case.

The Android glue is where the gaps are. Screenshot capture uses `MediaProjection`, which on modern Android must run under a `mediaProjection`-typed foreground service with the matching permission — neither is declared, so the capture path will throw. Pairing is one-directional in state: only the device that scans records a `PairedDevice`, so the device that showed the QR has nobody to send to. File reassembly cannot distinguish two simultaneous transfers in the same pairing. The relay client also binds to a single pairing, so a device paired into more than one group only syncs its first pairing over the far path.

1. **MediaProjection foreground-service type missing** — screenshot capture starts a projection but `SyncService` is declared `foregroundServiceType="dataSync"` with no `mediaProjection` type and no `FOREGROUND_SERVICE_MEDIA_PROJECTION` permission; on API 29+ this throws at `getMediaProjection`/`createVirtualDisplay`. Add a projection-typed foreground service (or elevate the service type during capture) and the permission.
2. **Initiator never records its peer** — `createPairing` stores the secret but no `PairedDevice`; only the scanner calls `acceptPairing`. The device that showed the QR has an empty `pairedDevices()` and can send nothing back. Have the initiator persist the peer once pairing completes (requires the peer's `DeviceInfo` to flow back, e.g. a relay hello exchange or a return QR).
3. **Concurrent transfers in one pairing collide** — an inbound chunk is attributed to `firstOrNull { key startsWith "pairingId:" }`, so two files sharing a pairing interleave into one `InboundTransfer` and corrupt each other. Carry a transfer id in `FileChunkPayload` (and in `FileMetaPayload`) and key reassembly on it.
4. **Short-code pairing is cosmetic** — `generateShortCode()` is shown as status text but never stored or indexed, and the "short code" text field actually expects a full payload JSON. Either implement a relay-side pending-pairing index that resolves a code to a payload, or drop the short-code affordance and label the field "paste pairing payload".
5. **Relay client bound to a single pairing** — `SyncService` opens the relay socket under `pairedDevices().firstOrNull()?.pairingId`, so a device in multiple pairings only receives far-path traffic for its first one. Open a socket (or multiplex) per pairing.
6. **TransportRouter can double-deliver** — on a LAN send that reports a peer but fails, it retries over the relay; if the LAN write actually landed, the peer gets the envelope twice. Receivers aren't idempotent for clipboard. Consider a dedup/message-id or make the fallback explicit about at-least-once semantics.
7. **QR embeds the full long-lived secret with no rotation** — documented as a proximity trust assumption, but the secret is static and grants permanent decrypt ability; a leaked/retained QR image is a standing compromise. Consider rotation or an authenticated ephemeral key exchange in a later phase.

### One sealed Envelope, two transports

LAN and relay carry byte-identical `Envelope` JSON; only the framing differs (4-byte length prefix on the socket, WebSocket text frame on the relay). `EnvelopeCodec` is the single seal/open bridge used by both the app and the relay tests, which keeps the two paths from drifting into separate implementations — the relay test asserts byte-for-byte envelope equality after a round trip and then decrypts with the shared link key, so a divergence between what the app seals and what the relay forwards would fail the suite.

```
copy/screenshot/file  ──seal (AES-256-GCM, per-link key)──▶  Envelope(JSON)
                                                               │
                              ┌────────────────────────────────┤
                        LAN (NSD + TCP)                   relay (WS)
                     Framing length-prefix            Frame.Text, offline queue
                              └────────────────────────────────┘
                                                               ▼
                                          open with same link key on peer
```

### Crypto and key handling

HKDF-SHA256 follows RFC 5869 (zero salt, counter-based expand), keys are 256-bit, seal uses a fresh 12-byte nonce and 128-bit GCM tag, and context separation is real (`"clipboard"` vs `"file-transfer"` yield independent keys, asserted). Secrets come from `SecureRandom`, live only in Keystore-backed `EncryptedSharedPreferences`, and link keys are derived on demand, never written to disk — no hardcoded key material anywhere.

The standing security caveat for later phases: the pairing secret embedded in the QR is long-lived and static, with no rotation or forward secrecy, so a retained QR image is a permanent decryption capability. Reasonable as a documented proximity assumption, but worth closing with rotation or an ephemeral key exchange.

### Relay is zero-knowledge, and defends its routing metadata

`RelayHub` holds no key and calls no decrypt path — confirmed by reading `relay/src/main` end to end. Routing is purely on cleartext `pairingId`/`fromDeviceId`/`toDeviceId`. The handshake `Hello` binds a socket to one `(deviceId, pairingId)`, and every subsequent frame is rejected unless its `fromDeviceId` and `pairingId` match, so a client can't speak as another device or inject into another pairing; the cross-pairing isolation test confirms a device in `pair-2` receives nothing destined for `pair-1`. The offline queue is TTL- and count-bounded with oldest-eviction, flushed on `register`, and the offline-delivery test drives the asleep-peer case end to end.

A behavioral asymmetry in the queue: `routeEnvelope` only parks an envelope when `toDeviceId` is a specific disconnected peer. A broadcast-style envelope (empty `toDeviceId`) delivered to zero live peers is dropped silently. The app always addresses a concrete `to` today, but a future caller sending unaddressed envelopes would lose them with no backlog.

### Remote operation path

`RelayClient.connect` keeps a WebSocket open with capped backoff (1s→30s) and re-handshakes on reconnect; `TransportRouter.send` prefers LAN when `hasPeer`, else relay, with a cross-fallback. Run from the foreground `SyncService`, the socket stays alive on mobile data with the screen off — the concrete realization of the far-away requirement.

The fallback has a double-delivery edge: if `lan.send` reports a peer and throws after the bytes were already written, the router also sends over the relay, and the peer receives the clipboard/file envelope twice. `onEnvelope` for clipboard is not idempotent (it will re-set the clipboard and re-notify). A message id with receiver-side dedup would close this.

### Screenshot capture will fault on modern Android

`ScreenshotCapture` acquires a `MediaProjection` and spins a one-shot `VirtualDisplay`+`ImageReader`, which is the right shape, and its own doc comment states that API 29+ requires starting projection from a `mediaProjection` foreground service. But `SyncService` is declared `android:foregroundServiceType="dataSync"` only, and the manifest requests `FOREGROUND_SERVICE_DATA_SYNC` but not `FOREGROUND_SERVICE_MEDIA_PROJECTION`. On API 29+ (and hard-enforced on API 34, the configured `targetSdk`) `getMediaProjection`/`createVirtualDisplay` throws a `SecurityException`. The capture flow therefore cannot work as shipped. Fix needs the projection foreground-service type plus the matching permission, and the projection must be started while that typed service is in the foreground.

`imageToBitmap` reconstructs from `ImageReader` row stride and crops the padding — stride handling is a common source of skewed/garbled screenshots on some devices (possible; verify on-device once the service-type fix lands).

### File/photo transfer and reassembly

Sending hashes the content (SHA-256), sends a sealed `FileMetaPayload`, then sealed 256 KiB `FileChunkPayload`s, and reassembly verifies the digest before saving (failed hash discards). Meta-vs-chunk disambiguation relies on the two payload shapes having disjoint required fields, which holds.

The reassembly keying is the problem. A chunk carries no file/transfer identifier, so `onEnvelope` attributes every inbound chunk to the first in-flight transfer for that pairing. Two concurrent transfers in the same pairing (e.g. the user shares two photos, or a screenshot lands mid file-send) interleave into one `InboundTransfer`; the SHA check then fails and both are discarded at best, or one silently corrupts the other. The fix is a transfer id threaded through meta and chunks, with reassembly keyed on it rather than on "first match for pairing."

### Pairing records only one side

`PairingManager.acceptPairing` persists the secret and records the initiator as a `PairedDevice` on the scanning device. But the initiator (`createPairing`) only persists its own secret under the new `pairingId`; it never learns the scanner's `DeviceInfo` and never adds a `PairedDevice`. Since clipboard and file sending both iterate `pairing.pairedDevices()` and skip when empty, the device that displayed the QR has no peers to send to — sync works only in the scanner→initiator direction until the initiator independently pairs the other way. Phase 1's own flows (copy on A, see on B) assume bidirectional pairing, so this needs the peer's identity to flow back to the initiator (a relay-mediated hello, or a confirmation frame carrying the scanner's `DeviceInfo`).

Relatedly, the short-code story is incomplete. `generateShortCode()` produces a code that `DevicesScreen` shows as status text but never stores or registers anywhere, and no relay endpoint resolves a code to a pending `PairingPayload`. The "Enter pairing payload / short code" field is wired to `acceptPairing`, which expects full payload JSON — a typed 8-char code will just fail to parse. Either build the pending-pairing index (initiator or relay holds `code -> payload`, hands it to the presenter) or remove the short-code affordance for Phase 1 and relabel the field.

### Multi-pairing limitation on the relay client

`SyncService` connects the relay under `pairedDevices().firstOrNull()?.pairingId ?: deviceId`. A device paired into more than one group (phone↔tablet and phone↔laptop as distinct pairings) only receives far-path traffic for the first pairing; the LAN path is unaffected because it isn't pairing-scoped. Labelled a later-phase concern in-code, but it caps remote sync to a single pairing today.

### Test coverage

`:core` and `:relay` tests exercise real logic, not mocks: AES round-trip, wrong-key failure, HKDF determinism and context separation, key/nonce sizes, pairing payload round-trip with secret integrity, framing, and relay forwarding/isolation/offline-flush using the real codec. These would fail if the implementation were reverted. Both suites are green on JDK 17 (21 + 4).

Not tested (and mostly untestable here without the Android SDK, but worth noting as risk surface): the `TransportRouter` LAN↔relay fallback and its double-delivery edge; `FileShare` concurrent-transfer reassembly (a pure-JVM test of `FileShare`'s chunk logic is feasible if the Android I/O were factored out, and would have caught the attribution bug); the MediaProjection/foreground-service-type contract; and the pairing bidirectionality. The chunk-reassembly and router-fallback logic are plain Kotlin that could be lifted into testable units.
