# Linkup Phase 1: re-review after the v1 fixes (v2)

This pass checks the six confirmed v1 bugs the coder addressed plus the deferral of the seventh, and looks for regressions the fixes introduced. The changes are real and well-targeted: concurrent file transfers now carry a `transferId` and reassembly moved into a pure-JVM `:core` `FileReassembler` with a genuine interleaved-transfer regression test; pairing became bidirectional via a sealed `PAIRING_HELLO` the scanner sends back to the initiator; the MediaProjection screenshot path now has the `FOREGROUND_SERVICE_MEDIA_PROJECTION` permission and the service elevates to the `mediaProjection` type around capture; the relay client multiplexes one socket per pairing; and the LAN↔relay fallback dedups on `(fromDeviceId, pairingId, nonceB64)`. The relay was not touched and remains zero-knowledge (no decrypt/open call anywhere in `relay/src/main`, verified). Core+relay suites are green on JDK 17 (28 + 4 = 32).

Watch for: the relay client's pairing list is a one-time snapshot taken when the service/router is constructed, so a pairing created or accepted *after* startup gets no relay socket until the process restarts — on a fresh install, where the service starts with zero pairings, the user's first pairing never reaches the far path until a restart (confirmed). This weakens the headline "works when the phone is far away" requirement right after onboarding. The six fixes are otherwise sound; this is a new gap exposed by the per-pairing multiplexing design, not a v1 regression in the strict sense.

**Verdict**: NEEDS_CHANGES

## High-level view

Issue 3 (concurrent-transfer collision) is fully resolved and is the strongest fix of the batch. The protocol now carries a `transferId` on both `FileMetaPayload` and `FileChunkPayload`, and reassembly is a pure-JVM `FileReassembler` keyed on `pairingId:transferId`. The regression test interleaves two transfers in one pairing and asserts both complete intact — it would fail under the old "first in-flight transfer" attribution, so it genuinely locks the fix in.

Issue 2 (one-directional pairing) is resolved cleanly. A new `TransferKind.PAIRING_HELLO` + `PairingHelloPayload` let the scanner seal its own `DeviceInfo` back to the initiator, which records it via `PairingManager.recordPeer`. The hello rides the same sealed-envelope path, so the relay still never learns who pairs with whom. Both the scan and paste flows trigger it.

Issue 1 (MediaProjection service type) is resolved. The manifest declares `foregroundServiceType="dataSync|mediaProjection"` and the `FOREGROUND_SERVICE_MEDIA_PROJECTION` permission, and `SyncService` elevates the running foreground service to include the `mediaProjection` type for the duration of a capture, then restores the data-sync-only type. Cannot be assembled here (no Android SDK), judged by code.

Issue 5 (relay bound to one pairing) is addressed by `RelayClient` multiplexing one auto-reconnecting socket per pairing id — but the id *list* is captured once at construction and never updated, which is the new concern above. The multiplexing itself is correct; the subscription set is stale.

Issue 6 (double-delivery) is addressed with receiver-side dedup on `(from, pairing, nonce)`. The characterization is correct: each `seal` draws a fresh random nonce, so the duplicate from a fallback carries the *same* nonce (deduped) while a legitimate re-send carries a *new* nonce (not deduped). The dedup set is bounded (512 entries, LRU eviction).

Issue 4 (cosmetic short code) is addressed in the UI: the field is relabeled "Paste pairing payload", the fake short-code status is gone, and `DevicesScreen` documents that no short-code resolution exists in Phase 1. A stale `generateShortCode()` remains in `:core`/`PairingManager` and the ARCHITECTURE diagram still lists the short code as a present pairing branch — cosmetic doc drift, not a functional gap.

Issue 7 (static long-lived QR secret) is deferred to Phase 3 with written justification in SECURITY.md and ARCHITECTURE.md. Reasonable: it was framed as a later-phase hardening item in v1, the proximity-trust mitigation is documented, and no code regressed it.

### Concurrent transfers: fixed, and the test proves it

`FileChunkPayload` and `FileMetaPayload` now carry a `transferId`, and `FileShare.sendBytes` stamps a fresh `UUID` on the meta and every chunk of a transfer. Reassembly moved out of the Android layer into `:core`'s `FileReassembler`, keyed on `"$pairingId:$transferId"`, so two overlapping transfers in one pairing land in separate `InboundTransfer` buffers. `FileShare.onEnvelope` now just decrypts, routes meta vs chunk by shape, and delegates to the reassembler under a lock (`FileReassembler` is documented not-thread-safe and the app guards every call).

The regression test (`two concurrent transfers in one pairing do not corrupt each other`) interleaves A0, B0, B1, A1 and asserts both complete with their own bytes and names. Under the old attribution — "first in-flight transfer for this pairing" — B's chunks would have been folded into A, failing both SHA-256 checks; the test therefore fails without the `transferId` keying, which is exactly what a regression test for this bug should do. A companion test (`same transferId in different pairings stays isolated`) covers the cross-pairing key collision, and the resize branch (meta's size estimate disagreeing with the sender's `totalChunks`) is handled by trusting the chunk's `totalChunks` and recounting surviving slots.

### Bidirectional pairing over whichever transport is live

The scanner path (`acceptPairing`) records the initiator from the QR, then `DevicesScreen` fires `handshake.announceToInitiator(self, paired)`, which seals a `PairingHelloPayload` (the scanner's own `DeviceInfo`) under the shared link key and sends it as a `PAIRING_HELLO` envelope. On the initiator, `SyncService.dispatchIncoming` routes `PAIRING_HELLO` to `PairingHandshake.onEnvelope`, which opens it and calls `recordPeer` (a no-op if already known). Both the camera-scan and paste-payload buttons invoke the announce, so both pairing entry points become bidirectional. Because the hello is a normal sealed envelope, it also traverses the relay, so the far-away pairing case is covered — subject to the relay-socket-subscription gap below.

One behavioral note, not a blocker: `announceToInitiator` is best-effort — if neither transport is up at the moment of pairing (`router.send` silently no-ops when both paths fail), the initiator never learns the peer and nothing retries. The LAN path makes this unlikely for same-room pairing, but a pairing done entirely off-LAN before the relay socket for that pairing exists (again, the subscription gap) could leave the initiator one-directional. A hello re-send on first successful connect would close it.

### MediaProjection foreground-service type

The manifest now carries `FOREGROUND_SERVICE_MEDIA_PROJECTION` and declares the service as `dataSync|mediaProjection`. `SyncService.captureScreenshot` elevates the running service to include `FOREGROUND_SERVICE_TYPE_MEDIA_PROJECTION` before acquiring the projection and restores the data-sync-only type in a `finally`. This is the ordering API 29+/34 require, so the `SecurityException` at `getMediaProjection`/`createVirtualDisplay` the v1 review flagged no longer applies. Unverifiable without the Android SDK, but correct by inspection.

The v1 "possible" note on `imageToBitmap` stride handling is unchanged by this fix and remains an on-device verification item, not a code defect.

### Relay client multiplexes per pairing — but the pairing set is frozen at startup

`RelayClient` now takes a `List<String>` of pairing ids and runs one `connectPairing` loop each, keeping a `ConcurrentHashMap<pairingId, session>` so `send` picks the socket matching `envelope.pairingId`. Each loop has its own capped backoff and re-handshakes on reconnect. This correctly fixes the v1 "only the first pairing syncs" bug for pairings that exist when the client is built.

The gap: the id list is immutable and sampled once —

```
SyncService.onCreate / LinkupContainer.router:
    pairingIds = pairedDevices().map { pairingId }.distinct()
                   .ifEmpty { listOf(deviceId) }   // fresh install → [deviceId]
RelayClient.connect(): launches one connectPairing(id) per id, then never changes the set
```

There is no `addPairing`/re-subscribe API. Consequences:

- Fresh install: the service starts with no paired devices, so the only socket comes up bound to `(deviceId, deviceId)`. After the user pairs, far-path envelopes for the new `pairingId` are routed by the relay under that pairing — a key no socket is handshaked for — so nothing arrives until the app process restarts and re-samples `pairedDevices()`. The LAN path masks this on the same Wi-Fi, but the "phone is far away" case (the explicit user requirement) is exactly where there is no LAN peer, so first-pairing remote sync silently does nothing until a restart.
- Adding a second pairing later (phone↔laptop after phone↔tablet) has the same problem for the newly added pairing.

The fix is a dynamic subscription: expose `RelayClient.addPairing(id)` that launches a `connectPairing(id)` into the connect scope, and call it from the pairing completion paths (`createPairing`, `acceptPairing`, `recordPeer`). The multiplexing machinery is already there; only the ability to grow the set at runtime is missing.

### Fallback dedup is correct and bounded

The v1 cross-fallback (try preferred path, on failure try the other) is unchanged; the receive side now drops duplicates by `(fromDeviceId, pairingId, nonceB64)` before emitting on `incoming`. The identity choice is sound and does not risk dropping legitimate re-sends: `E2E.seal` draws a fresh 12-byte random nonce per call, so the same sealed envelope delivered twice (LAN write landed but reported failure, then relayed) carries an identical nonce and is deduped, while any legitimately re-sent payload is re-sealed with a new nonce and passes through. The dedup map is an LRU bounded at 512 under a lock; a duplicate from the fallback arrives back-to-back, well inside that window, so eviction won't resurrect it.

### Relay untouched and still zero-knowledge

The fix commit does not modify `relay/src/main`. Re-reading it confirms `RelayHub` holds no key and calls no `open`/decrypt/`deriveLinkKey`; routing is purely on cleartext `pairingId`/`fromDeviceId`/`toDeviceId`, the Hello handshake still binds a socket to one `(deviceId, pairingId)` and rejects spoofed frames, and the TTL/count-bounded offline queue is unchanged. The zero-knowledge property the far-path requirement depends on is intact.

### Test coverage of the fixes

`:core` grew to 28 tests: the `FileReassembler` suite (single multi-chunk, concurrent interleave, unknown chunk, integrity failure, empty transfer, cross-pairing isolation) and the `EnvelopeCodec` `PAIRING_HELLO` round trip. These exercise real logic and would fail if reverted. Not tested: the end-to-end bidirectional handshake wiring (scanner announce → service dispatch → `recordPeer`), the `TransportRouter` dedup/fallback, and the relay-pairing subscription lifecycle. The last of these is where the startup-snapshot gap lives; a small JVM test of a dynamic-subscription `RelayClient` (or a router-level test) would have surfaced it. The app layer can't be assembled here, but the dedup and subscription logic are plain Kotlin that could be factored into testable units as the reassembler was.
